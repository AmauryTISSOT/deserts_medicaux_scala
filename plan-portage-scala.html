HealthMap — portage de l'application Python vers Scala 3

Réimplémentation de l'application Streamlit open_data_health_map en Scala 3 full-stack, avec Scala.js côté navigateur et DuckDB côté serveur.

Source : Python / Streamlit Cible : Scala 3.3 LTS Jeu de données : 432 015 lignes Volume estimé : ~1 500–2 000 lignes

1. Point de départ

Le dépôt source contient une application Streamlit d'environ mille lignes utiles : un fichier Parquet de 432 015 professionnels de santé (colonnes code_postal, commune, profession, nom, prenom, latitude, longitude), quatre onglets — carte à points, choroplèthes par région et par département, page d'informations, assistant IA — des agrégations DuckDB/pandas et des cartes Plotly.

Le dépôt cible est vide. Il s'agit donc d'une réimplémentation complète, et non d'une migration incrémentale : rien ne peut être porté fichier par fichier.

Contrainte structurante

Scala.js s'exécute dans le navigateur et ne sait pas lire du Parquet. Le « full-stack Scala.js » se traduit donc par un serveur JVM (accès aux données et API) et un client Scala.js (interface), reliés par un module shared compilé pour les deux plateformes. C'est ce module partagé qui apporte le typage de bout en bout — l'intérêt principal du choix.

Modèles et référentiels

MapPoint, RegionCount, DeptCount, CoverageAnalysis, ChatResponse et leurs codecs upickle. On y centralise aussi les tables aujourd'hui dupliquées dans le Python : département → région, noms de départements, symptômes → spécialités.

server

Données et API

DuckDB en JDBC lit directement le Parquet — même moteur que l'original. Agrégations en SQL, résultats mémoïsés au démarrage, exposition en REST via http4s.

client

Interface réactive

Laminar pour la structure et l'état (Var / Signal), façades Scala.js vers Leaflet pour les cartes et Chart.js pour les graphiques.

3. Déroulé par phases

Phase 0

Chaîne d'outils

JDK 21 Temurin et sbt installés via winget, puis vérification de sbt --version. Node et npm sont déjà présents sur le poste pour le bundling Scala.js.

Phase 1

Squelette de build

build.sbt en cross-project sur Scala 3.3 LTS, fastLinkJS côté client, et une tâche sbt unique qui lance le serveur avec rechargement du client.

Jalon : une page servie sur localhost:8080 affichant un élément rendu par Laminar.

Phase 2

Données

Copie de fichier_professionnels_avec_coords.parquet (7,5 Mo) dans data/. Le JSON des communes pèse 62 Mo et n'a pas sa place dans Git : pipeline/fetcher.py est porté en un job Scala optionnel (sbt pipeline/run) capable de régénérer l'enrichissement depuis les sources brutes, celles-ci restant ignorées par Git.

Phase 3

Couche données serveur

ProfessionalRepository au-dessus de DuckDB JDBC, avec read_parquet direct et agrégations en SQL. Les résultats sont mémoïsés au démarrage : l'application Python rechargeait le Parquet à chaque onglet et à chaque interaction.

Phase 4

API http4s

Mise en place des routes ci-dessus, sérialisation par les codecs du module shared, service des fichiers statiques et du bundle JavaScript.

Phase 5

Client Laminar

Structure à quatre onglets, état réactif pour le filtre profession, appels d'API typés grâce aux modèles partagés, indicateurs de chargement.

Phase 6

Cartographie

Façade Scala.js vers Leaflet : couche de points avec clustering — l'équivalent du scatter_mapbox sur 6 000 points — couches choroplèthes région et département avec échelle de couleur et légende, fond de carte OpenStreetMap.

Phase la plus lourde : Plotly fournissait ces cartes clés en main, il faut ici les construire.

Phase 7

Graphiques et tableaux

Classement des 10 communes les mieux dotées, tableaux triables par région et par département, histogramme départemental.

Phase 8

Assistant IA

Portage de HealthMapChatbot : extraction des symptômes, correspondance vers les spécialités, analyse de la couverture départementale. Client HTTP vers Ollama (http://localhost:11434, modèle mistral) avec les mêmes messages d'erreur en cas d'indisponibilité, et interface d'onglet avec historique.

Phase 9

Packaging

sbt-native-packager pour un lancement en une commande, README (installation, lancement, sources de données, équipe), .gitignore Scala complété.

4. Anomalies de l'existant

Relevées à la lecture du code source. Elles sont corrigées au passage plutôt que reproduites à l'identique.

EmplacementConstat
app_streamlit.py:305 get_dept_from_cp teste cp_str.startswith("2A"), alors que les codes postaux corses sont numériques (20xxx) : la Corse n'apparaît jamais sur la choroplèthe départementale. utils/data.py applique par ailleurs une logique différente et incompatible ("2A/2B").
app_streamlit.py · dept_names "79" est libellé « Nièvre » au lieu de « Deux-Sèvres » — "58" porte déjà ce nom.
utils/charts.py create_map_chart référence des colonnes météorologiques (summary_current_temp) absentes du jeu de données : code mort provenant d'un autre projet. Non porté.
utils/geo.py, pipeline/ geo.py est commenté à 90 % ; main.py, storage.py et transformer.py sont vides.
app_streamlit.py load_data() est appelé trois fois sans @st.cache_data, rechargeant l'intégralité du Parquet à chaque rerun.

5. Point à trancher en équipe

Décision produit

Le projet s'intitule « déserts médicaux », mais l'application ne calcule que des effectifs bruts : Paris arrive en tête simplement parce qu'elle est peuplée. Une mesure réelle de désert médical suppose une densité pour 100 000 habitants. Le JSON des communes contient vraisemblablement la population, ce qui permettrait d'ajouter l'indicateur en phase 7.

Le portage part par défaut sur un comportement identique à l'existant. Cet ajout reste à valider ensemble — c'est l'argument le plus solide en soutenance.

6. Répartition du travail

Cinq lots, découpés pour que chacun soit propriétaire de fichiers distincts : les conflits de fusion restent ainsi marginaux. Chaque lot regroupe des phases cohérentes et se termine par un livrable vérifiable indépendamment.

Prérequis au parallélisme

Deux verrous conditionnent tout le reste et doivent tomber en premier : le squelette de build (lot A) sans lequel personne ne compile, et le contrat d'API — modèles et codecs du module shared, plus la liste figée des endpoints (lot C). Une fois ces deux points livrés, les lots B, C, D et E avancent réellement en parallèle ; les lots D et E travaillent sur des réponses simulées tant que le serveur n'est pas branché.

Règles de collaboration

  • Une branche par lot (lot-a-build, lot-b-data, …), fusionnée dans main par petites incréments plutôt qu'en une fois à la fin.
  • Le module shared n'est modifié que par le lot C ; toute demande d'ajout passe par lui, ce qui évite les conflits sur le fichier le plus transversal du projet.
  • Les lots D et E consomment des jeux de données factices tant que l'API réelle n'est pas prête — aucune attente mutuelle.
  • main doit compiler à tout moment : c'est la branche de démonstration.
Note d'effectif

Le README du projet source recense quatre membres (Adrien Fouquet, Amaury Tissot, Léa Druffin, Satya Minguez), alors que ce découpage prévoit cinq lots. À cinq, l'attribution est directe. À quatre, la solution la plus naturelle est de confier les lots A et C à la même personne — ils s'enchaînent chronologiquement et partagent la même exigence de livraison rapide.
